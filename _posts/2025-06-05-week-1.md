Hi, I'm Zixin, I am a third-year PhD student in the Univeristy of Glasgow. In GSOC 2025, I will work on the development of Flow Refueling Location Models (FRLMs) for PYSAL. 

This project aims to extend PySAL's spatial optimiisation library (spopt) by implementing flow-based facility location models, specifically, the basic FRLM, threshold extention FRLM, Capacited FRLM, 
and Deviated FRLM.  For example, in the field of transport facility planning, facility loca8on models have evolved from nodes-based to flow-based approaches to better capture demand as traffic flows passing by a facility.

Before the start of the project, I already had the code for the basic FRLM but it was not in an OOP format. I was also not familiar with the process of open-source package development. To start, I familiarised myself with how to:

- Fork a repository
- Clone my forked repository to set up a local development environment
- Create branches for different features and bug fixes
- Commit changes and push changes to my fork on GitHub
- Create pull requests to propose changes to the main repository

After getting familiar with the worflow, I started to change my code into an OOP format. With the help of my mentors, I have learned some aspects specific to open-source coding, which is different from coding my own research projects before. 

- 1. Code Simplification and Class Structure
Initially, I was not aware of the simplicity principle in code design. I had created separate classes for the capacitated model and basic model, but my mentors pointed out that it would be better to consolidate them into one class. Instead of having multiple classes, users should simply set the appropriate parameters to switch between model types. This approach makes the API more intuitive and reduces code duplication.

- I learned to be more careful with default values, ensuring they are common enough to be widely applicable. For example, instead of arbitrary values, defaults should be meaningful like "300 miles for distance thresholds" or "10% of the longest path for capacity limits." These defaults should make sense to users in real-world scenarios and provide a good starting point for most use cases.

- 3. Code Quality and Pre-commit Hooks
I implemented pre-commit hooks, particularly using Black for automatic code formatting. This ensures consistent code style across the entire project and catches formatting issues before they reach the repository.

- 4. Proper Result Exposure and API Consistency
One crucial improvement was exposing the results of the greedy solver properly. Users need access to:

Lagrange multipliers for optimization insights
Feasibility status through the .pulp attribute
Consistent API regardless of the underlying solver

The challenge is maintaining API consistency when users switch between different solvers (not just PuLP). Each solver may have different internal structures, but our package should present a unified interface.
